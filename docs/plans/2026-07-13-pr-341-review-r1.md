### Task 1: Make Switch Wipe Failure Atomic and Retryable (comments #1, #2)

**Review comments addressed:**
- Sourcery inline at `Foqos/CloudKit/ProfileSyncManager.swift:397`: avoid swallowing `ModelContext.save()` errors and do not reset emergency state if the SwiftData wipe failed.
- Greptile inline at `Foqos/CloudKit/ProfileSyncManager.swift:366`: failed wipe must not resume/re-attach the new account.

**Evidence:**
- `resolveConflictSwitchToCloud()` calls `wipeLocalSyncedDataDirectly()` and then always reattaches the new account and clears pause.
- `wipeLocalSyncedDataDirectly()` currently uses `try?` around fetch/delete/save calls and then resets emergency state unconditionally.
- Reattaching after a failed wipe with `forceSeed=false` can seed leftover local data into the new account's fresh namespace, silently turning Switch into an unconsented Combine.

**Required behavior:**
- `wipeLocalSyncedDataDirectly(...)` must fail explicitly on fetch, model-owned delete, or final save failures.
- On wipe failure:
  - rollback any pending SwiftData changes where applicable,
  - log with `Log.error(..., category: .sync)`,
  - keep `.accountChanged` pause and conflict state so Settings can re-prompt and retry,
  - do not reattach the engine,
  - do not clear pause,
  - do not reset emergency state.
- On wipe success:
  - continue to use `BlockedProfiles.deleteProfile(_:in:cleanup:)`,
  - continue to use `SavedLocation.delete(_:in:)`,
  - reset emergency state only after the SwiftData wipe has succeeded,
  - reattach and clear pause as before.
- Do not use raw `context.delete` for Switch wipe.
- Do not touch reset-zone/deleteZone/§8.1 machinery.

**Tests:**
- Add focused coverage in `ProfileSyncAccountResolverTests.swift` or a nearby account resolver test file.
- Include a failed-wipe test whose comment states the real stake: failed Switch wipe plus reattach can seed leftover local data into a new fresh namespace, silently turning Switch into unconsented Combine.
- The failed-wipe test must assert: pause/conflict remains re-promptable, no reattach, no emergency reset.

### Task 3: Own and Cancel Account-Resolution Retry Task (comment #4)

**Review comment addressed:**
- Sourcery general feedback: retry delay is hard-coded and retry task lifecycle is not explicit.

**Evidence:**
- `scheduleAccountResolutionRetry()` creates a discarded task with an inline `5_000_000_000` delay.
- `Task.sleep` is cancellable, but the task handle is not retained and cancellation is not observed.
- A stale retry can fire after sync has been disabled and re-enter account-change handling.

**Required behavior:**
- Add a manager-owned retry task handle.
- Centralize the retry delay in a private constant or similarly scoped value.
- Cancel the retry task on disable.
- Cancel the retry task on every confirmed account-resolution outcome.
- Return early on cancellation.
- Guard `isEnabled` inside the retry task before re-entering account-change handling.
- Full user-configurable retry delay is not required.

**Tests:**
- Add focused tests proving retry scheduling can be suppressed/canceled and does not fire after disable or confirmed resolution.
- Existing resolver tests that disable retries for determinism should remain deterministic.
