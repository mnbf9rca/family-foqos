# Shortcuts start policy and Siri phrases

Issues: [#485](https://github.com/mnbf9rca/family-foqos/issues/485), [#486](https://github.com/mnbf9rca/family-foqos/issues/486). Baseline: `91893b8825b908b4144e3caaf5c1312e79f275f9` (`main`). Write-up only; the reviewed spec PR stays open for a build stream to inherit and lands with implementation.

## Accepted inputs and boundaries

The human accepted build2's reviewer-approved research, `docs/superpowers/research/2026-09-10-app-intents-ios27.md`, available in `/Users/rob/git/family-foqos/.worktrees/build2-app-intents-research`. This design uses that research; it does not repeat the Apple research or adopt new iOS 27 features. Retain the iOS 18.6 deployment target and the four existing intent identities.

The human chose an explicit per-profile Siri/Shortcuts start trigger, one device-wide unlock setting covering both start and stop, and exactly three spoken actions: start a named profile, stop a named profile, and current blocking status. No ad hoc app selection, Clock schema, breaks, emergency escape, voice editing, or family remote control; closed issues #487–#491 stay closed. Profiles, sessions, tags, and locations remain private to the owning account. The existing private-account session sync gains the timer deadline and the ownership/adoption handling specified below; nothing crosses the family share.

**Migration clarification from the orchestrator:** an absent start-permission field defaults from `manual`. Tag-only profiles do not retain their existing Shortcuts bypass. An authorized editor can enable the new trigger alongside tags; there is no legacy exception. Issue #485 must carry this same migration rule.

## Decision

Add `ProfileStartTriggers.shortcuts` and enforce it inside `StrategyManager.startSessionFromBackground`, where saved identifiers and Siri requests converge. Require valid stop conditions and a stop route usable without a scanned start tag. Without a supplied duration, reuse the existing manual session lifecycle after those gates pass. Treat a supplied duration as an override for this execution only, permitted by the existing profile edit gate: arm the session timer without writing the override into the profile. Define the stop-reachability rule once for the available start credentials; separate issue [#493](https://github.com/mnbf9rca/family-foqos/issues/493) applies the same function to the Start button.

Add one “Require Device Unlock” toggle under Settings → Siri & Shortcuts, default **on**, applying equally to start and stop. With one switch, the default must account for stopping as well as starting: an unattended voice request must not stop even a voluntarily stoppable block by default. Turning it off permits both eligible operations while locked, subject to system availability and all profile rules. This trades some phone-down convenience for deliberate initial behavior; users who want unattended automations can opt out.

Package `StartProfileIntent`, `StopProfileIntent`, and `CheckSessionActiveIntent` in one `AppShortcutsProvider`. Keep `CheckProfileStatusIntent` available to existing automations without a packaged phrase. No new action catalogue, dependency, indexing service, or natural-language parser.

## 1. Profile permission and compatibility

Use the wire key `shortcuts` inside the existing trigger blob; no family-share or new CloudKit field. The UI label is “Siri and Shortcuts”, with one explanatory line: “Allow Siri and Shortcuts to start this profile.” It is independent of tap, tag, schedule, and deep-link permission and does not grant manual or Shortcut stop. Include it in `ProfileStartTriggers.isValid`. This is one combined control: a user shortcut can be run by its Siri name, and App Intents discoverability does not provide a separate per-profile Siri exclusion. Do not offer a Siri-only/Shortcuts-only choice.

Add an explicit `ProfileStartTriggers.init(from:)`: decode the existing keys as today, then decode `shortcuts` with `decodeIfPresent(Bool.self, forKey: .shortcuts) ?? manual`. The encoder always writes the Boolean. Adding a stored default without this decoder is insufficient: synthesized Codable would reject legacy blobs, and the profile getter would replace all their triggers with false. Test a real v3 JSON fixture without the new key. A present wrong-type value must fail decoding, not grant permission.

Preserve explicit true/false across save, reopen, cloning, and private-account sync. Do not keep recomputing it when manual changes after decoding. A new empty trigger configuration remains all false; the user selects its triggers explicitly. For v1 profiles, use the existing strategy migration first and initialize the new choice from the resulting manual trigger. No new schema migration is needed.

Keep profile schema 3 and the existing trigger blob. An older editor can omit the new key when it re-saves, resetting the choice on the updated reader to the manual-derived default; document that limitation and ask users to update their devices/recheck the switch. A schema bump would make whole profiles read-only on older devices while leaving their existing Shortcut bypass intact. This change does not claim to repair old binaries or enforce the new permission account-wide. Retain the existing unsupported-newer-profile refusal where applicable.

The new control inherits the editor's disabled state, temporary code unlock, and save-entry gate. A Child cannot change it on a locked profile without the existing code-authorized editor; a permitted start of that locked profile requires no extra parent-code prompt. Individual and Parent are not blocked by Child lock rules. Do not add a permission setter to an intent.

A profile with only this new start trigger is valid but tapping Start must not start it manually. Add a resolver explanation such as “Start this profile with Siri or Shortcuts.” Extend the exhaustive `StartAction` switches in HomeView without adding a new launch intent or a manual picker option. Mixed trigger profiles keep their existing in-app options.

## 2. Start execution and duration

Keep the existing intent type, profile parameter identifier, UUID entity identity, and optional `durationInMinutes` parameter identifier. Apple documents no behavior for removing an existing parameter; retain its identifier without promising how saved shortcuts would load after removal. Describe Duration as optional, applying to this execution only and unavailable while the existing profile edit gate is closed; no new spoken duration phrase.

A non-nil duration changes when this execution may end, so it must pass **the same `ProfileEditGate.editingDisabled` gate the editor uses today**. Supply the editor's current inputs: blocking state (local session or this profile remotely active), the profile's managed marker, current mode, `LockCodeManager.isUnlocked(profile.id)`, and `LockCodeManager.canVerifyCode`. Reuse the gate; do not replace it with a new lock matrix or omit temporary unlock/code availability. Resolve current profile data before evaluating it rather than depend on an editor view being open. Re-evaluate after any await, using the same current inputs as the editor.

When that gate is closed, refuse the duration before starting or arming a timer: “This profile cannot be changed right now. Remove Duration to use its configured stop conditions.” This is the expected outcome for a locked profile with no manual stop: `StrategyTimerActivity.stop` ignores manual-stop permission and could otherwise end the block early. Do not waive the gate because manual stop happens to be enabled; the existing gate decides access. Do not add a new intent-side code prompt. A nil-duration start does not change its stop behavior and remains allowed if the profile's start/stop rules allow it. Existing temporary unlock, code-availability, and mode behavior remains as defined by the editor and [the mode matrix](../../app-modes-and-locking.md).

When the gate permits it, validate the supplied duration against `DeviceActivityLimits.minimumIntervalMinutes` through `maximumTimerMinutes` and pass that value directly through the timed start to the existing timer registrar. **Never write it to `profile.strategyData`, change `updatedAt`, put it in a profile snapshot, or call `context.save()` to persist it.** Delete the existing duration-encoding/profile-update block. Do not mutate then restore the profile or put the override in a clone, defaults, or sync payload. It belongs only to this invocation's timer; the next start with no supplied duration must not inherit it.

Reuse `ShortcutTimerBlockingStrategy` and `startStrategyTimerActivity` with an explicit duration input for the Shortcut route, removing that route's dependency on stored `strategyData`. A concrete overload or a value on the fresh strategy instance is sufficient; do not widen every strategy's protocol or introduce a new timer/configuration type. Legacy NFC/QR timer callers may keep reading their existing saved settings through the existing entry point, delegating registration to the same implementation. Keep the current session lifecycle and timer cancellation on session end. The session deadline below is the sole new value, represented in the local session, SharedData, and the existing private-account session sync record; no profile field is added. The common start lifecycle may still publish the unchanged profile snapshot and session state; it must never encode or persist the override as profile configuration.

An accepted duration supplies this execution's timed stop through `StrategyTimerActivity`, independently of the profile's timer flag and `disableBackgroundStops`. It still requires all eligibility checks below, including the existing edit gate. Complete checks and any awaits before arming the timer. Invalid or refused duration must neither start a session nor schedule an activity.

At the shared background-start boundary, re-fetch the profile and active session and check all of the following before creating a session or applying restrictions:

1. The current invocation has passed the app-wide unlock policy; cancellation returns without mutation.
2. Profile exists and its trigger format is supported; any supplied duration passes the existing editor gate and bounds check; no session is active. A repeated start does not toggle, restart, extend, or replace a session. A failed active-session fetch refuses the request.
3. Screen Time authorization is approved and the profile has device-local selection (`needsAppSelection == false`). Read current `AuthorizationCenter.shared.authorizationStatus` through the existing `AuthorizationRequesting` seam (`AuthorizationCenterRequester.shared` in production), accepting `.approved` and `.approvedWithDataAccess` as `RequestAuthorizer` does. Do not construct the view-owned authorizer, add a wrapper type, request authorization silently, or synthesize app-selection tokens. Keep this check **only because a Shortcut start can run headless and bypass the app's foreground authorization handling**. The Start button relies on that foreground handling and needs no duplicate check in this spec. On refusal, instruct the user to open the app and authorize Screen Time. Do not claim that an approved status itself proves OS shielding.
4. `profile.startTriggers.shortcuts` is true. A saved UUID, a matching name, another enabled trigger, or an unlocked phone cannot override it.
5. `profile.stopConditions.isValid` is true, using the same primitive as the Start button. For a start without a supplied duration, additionally require a configured stop route usable with this invocation's credentials. An accepted supplied duration uses the existing timed strategy and supplies that exit; it still requires `stopConditions.isValid` and all other gates.

For check 5, define one small shared predicate beside the existing resolver, parameterized by the candidate start credential: **none, NFC, or QR**. Shortcut and tapped manual starts pass **none**, meaning no scanned start tag; retaining the modality lets the same function serve #493 unchanged. Count manual stop; specific NFC/QR stops; any NFC/QR stop unless shadowed by a same-tag condition whose start credential is absent; and scheduled/deep-link stop only when background stops are allowed. Follow `canStop`'s specific → same → any precedence. When a caller supplies a scanned-start credential, same-tag counts only for the matching NFC/QR start method; never treat a QR start as an NFC credential. These three input meanings are the contract; the implementer chooses their representation. Saved specific IDs and schedule data retain their existing form validation. Do not fetch location or build another configuration validator.

A selected `timer` flag alone does not count: the ordinary V2 manual-start path never arms `StrategyTimerActivity`. This is checkable in `ManualBlockingStrategy.startBlocking` and `StrategyManager.activateSession`, which registers only scheduled stops. With no supplied duration and no start scan, timer-only and same-tag-only profiles therefore refuse unless another route exists. Refusal explains “Use a start method that provides the required stop, or add a usable stop condition.” Do not add timer setup to the ordinary manual path, reuse a saved duration implicitly, or reuse the explicit override on later starts. The registrar accepts the invocation duration directly and reports the successfully registered deadline for the session-only field below. The explicitly supplied-duration branch above remains the existing exception because it actually selects the timer strategy; registration failure leaves no known timer deadline and is reported without claiming a timer was armed.

This is a credential rule shared by manual starts, not a Siri-specific validator. **#493, in a separate PR by human ruling, wires the Start button to this exact function**, evaluating the actual candidate start method so manual starts pass none and scanned starts pass NFC or QR to retain their matching same-tag stop. This PR defines and tests the common function and calls it from Shortcuts; #493 adds the tap caller rather than copying or redefining the predicate. Until #493 lands, the pre-existing tap hole remains for timer-only, same-tag-only, or schedule/deep-link-only stops with background stops disabled. The shortcuts-only Start-button explanation in section 1 remains in this PR.

Once those checks pass, a nil-duration start uses the same `ManualBlockingStrategy` lifecycle as a tapped start, with a nonphysical session tag and ordinary `forceStart: false`. A supplied-duration start passes its temporary value into `ShortcutTimerBlockingStrategy`, retaining its existing `forceStart` behavior. Keep activation, scheduled-stop handling, reminders, widgets, shared state, and same-account sync; do not call the universal-link toggle, legacy scanner UI, or the UI toggle that could stop an existing session. The action must propagate errors this lifecycle reports, including the existing scheduled-registration warning, and name the profile reloaded at execution time. A registration warning after activation must say the session started but its scheduled stop could not be registered; it must not say nothing changed.

This PR does not add a second transactional start or fix the common lifecycle's persistence ordering. `createSession` inserts/publishes without an explicit save, and the manual strategy's stop currently logs a save failure. Those pre-existing lifecycle limits apply to tap and Shortcut operation alike; do not claim this spec makes every start/stop durable before its dialog. Avoid success after an error the shared path actually reports, without creating parallel session/rollback machinery for Siri.

Preserve the optional start-geofence warning behavior rather than turn it into a hard stop restriction. If the existing warning setting is on and a start needs confirmation, continue in the foreground and use the existing warning flow before committing the start; cancellation has no effect. If location permission is absent, retain the current start-warning policy, which permits starting. After any authentication, warning, or location await, re-read active session and profile eligibility before starting.

Return the successfully resolved current profile name to the intent for its dialog. A renamed entity must not cause a stale success name. A successful response includes the accepted supplied duration for the timed branch, or says the profile started for the ordinary branch. Same-account sync failures retain the established local-session behavior and must not be described as cross-device completion.

### Session timer end time: completed path analysis

The human chose one session-level timer end field after code inspection disproved the proposed pinned-config calculation. `BlockedProfileSession.createSession` does not pin a profile; `RestrictionGrants.openBreakGrant` and `openOneMoreMinuteGrant` pin the live profile when the grant opens. That config can hold a different saved duration from this invocation's override. It is a restriction snapshot, not reliable evidence of an armed timer. Do not change its purpose or derive timer time from it.

Add optional `timerEndTime: Date?`, default nil, to `BlockedProfileSession`, `SharedData.SessionSnapshot`, and the existing `ProfileSessionRecord` sync representation. It means the planned end of the session countdown registered by its owning device; every device displaying that synced session receives the same timestamp. It is distinct from actual `endTime`, calendar stop schedules, `breakEndDeadline`, and `oneMoreMinuteDeadline`. On a receiving device it is read-only metadata: never arm/re-arm a countdown or end a session merely because this timestamp arrives or elapses. Only the device that armed the accepted countdown handles its expiry and sends the stop through session sync. Existing separately permitted manual or scheduled stop paths are unchanged. Never write it into a profile or `ProfileSnapshot`.

`startStrategyTimerActivity` is the single countdown registrar, called only by the three timer strategies. Have it report the absolute deadline after `startMonitoring` succeeds, using one captured registration time for both the OS interval and deadline. Share its existing upper clamp (`maximumTimerMinutes`, 1439) and hour/minute precision; compute the absolute end alongside the interval, including its date across midnight, rather than reconstructing it from a subsequently reconciled session start time. Do not introduce a new lower clamp: the Shortcut bounds check remains 15–1439 and the existing helper deliberately does not clamp lower values. OS delivery may be late; status reports timer time, not guaranteed enforcement.

Keep session creation before registration: `StrategyTimerActivity.start` can apply restrictions, so publish the session before the extension can act. Publish that successful deadline into the matching active session in SwiftData and SharedData before returning a successful start dialog. Use the existing session-ID checks/lock when updating shared state; do not overwrite a replacement session or replace the whole snapshot with a stale copy of grant fields. Save the session metadata with the current context and surface persistence failures. The human's ban on saving the override into the profile remains; this session-only save is explicitly allowed. If registration fails, leave/clear the field to nil and surface the timer failure; if registration succeeded but metadata publication fails, report that timing could not be saved. Neither error may claim the whole session rolled back: the existing strategy creates its session before registration. Keep reported warnings visible after common activation, which currently clears `errorMessage`; no new session transaction or automatic retry loop.

### Session sync wire: completed path analysis

**Human scope clarification:** V2 has no App Store users; its entire user base is TestFlight and updates concurrently. V1 is live in the App Store but never reads this field. There is no mixed-version beta window to engineer around for it. Add only optional `timerEndTime` as a native Date on the existing private-account `ProfileSession` record. Do not add a compatibility version, deadline envelope, session-generation token, extra owner field, or another record type. Reuse `startTime` and `sessionOriginDevice`, which the CAS record already has.

Keep the defensive reader check to one line: `guard isActive, let startTime, let timerEndTime, timerEndTime > startTime else { return nil }`. Missing, malformed, inactive, or non-later values read as absent. A later timestamp from a prior session is prevented at the writer: `resetForNewSession` clears it, and every new-session write supplies the new accepted deadline or explicitly removes the field. A decoder alone cannot identify a prior-session future timestamp; do not claim this guard does that. Apply the value together with its canonical profile/start identity, never to a different local session after an await. This is current-session correctness, not beta-compatibility machinery.
