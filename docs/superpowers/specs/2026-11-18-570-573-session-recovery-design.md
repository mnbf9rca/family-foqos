# Keep an ended session from returning (#570, #573)

After the iPad stopped After school at 18:04, it adopted the iPhone’s still-active record at 20:18. Separately, the iPhone was killed during a morning canonical identity change, inside ManagedSettings with the shared file lock held. Its morning profile later went from stopped sequence 32 to active sequence 33. A surviving old-ID row and reuse of its 06:00 start explain the sequence; the exact rows and payload were not recovered. The November 13 kill occurred in sync bookkeeping, a distinct stack. ## Admission and recovery contract

Use one V2 eligibility decision before activating a received record, joining a cloud winner, restoring a local row or retrying a start. Evaluate against **delivery time** and the current authoritative slot/completions. Exact ended instance, expired accepted countdown and an applicable independent stop occurrence since the actual start each bar resurrection. The stop recurrence applies to all origins, inclusive of equal clocks, subject to weekday and recurrence edit time. For a schedule-originated run, also compare its originating occurrence with the latest local stopped timestamp. Two devices may start minutes apart with different UUIDs in one occurrence. Preserve active multi-day runs and the next eligible occurrence, independent manual/tag starts after the stop, mirror timer ownership, legacy matching and live V1 sessions. Unknown origin never establishes schedule origin. Do not infer stale from age, offline duration, or a recently edited start schedule alone. Keep stopped timestamps monotonic across existing-profile sync and shared snapshot writes. [V2 rulebook](2026-10-02-508-v2-conditions-rulebook.md#independent-schedule-recurrences-515517)

A stale remote record can be retired using the existing identity-scoped stop outbox, after proving which record is stale. Never stop the whole profile on ambiguity. Retire a stale cloud winner without discarding a valid new originating candidate. Recheck the candidate before a retry. A genuinely newer live session must survive delayed stop, lookup, repair and network replies. Preserve remote-only controls for legitimate active records. Read or save failure defers adoption/publication and retains evidence for retry.

The shared slot identifies the V2 owner. The app consumes completions idempotently before adopting or publishing. A completed snapshot stays recoverable until history has been explicitly saved and the required stop intent recorded. A killed process can leave shared identity B with SwiftData row A. Reconciliation must be safe after interruption at *any* boundary: keep B if still live, end obsolete A and clear its pending start, preserve valid history and remove duplicate active status, including split states created by released builds. A nil end alone cannot grant permission to re-enforce or write a cloud start. The app reconciles the visible owner when it resumes and before any remote action or retry uses a published session.

## Lock and effect ordering

Mutate and verify shared ownership under the file lock. Perform ManagedSettings, DeviceActivity, SwiftData saves, UI and other service side effects after unlocking. Cover both changed-ID reconciliation and direct remote adoption plus all session/grant callers of shared transition callbacks. Avoid moving a stale captured activate/deactivate into an asynchronous task. Derive the effect from the committed current owner and grant, apply after unlock, recheck state after the external call and repair if another writer won. Relaunch reconciles effects for the surviving owner if the prior process died after commit or during application. No new lock around XPC. Preserve fail-closed behaviour on unreadable state and monitor lock contention. This addresses the observed adoption stack; it cannot guarantee the OS never suspends during a short storage transaction.

Log a stable privacy-safe correlation value derived only from the ephemeral session UUID at committed origin start, accepted stop and adoption, including old→canonical identity changes. Supply the same value in app and extension exports. No profile name, device or account identifier, tag payload, or location in these new messages. Update the lifecycle documentation to track observed defects and their verified dispositions.
